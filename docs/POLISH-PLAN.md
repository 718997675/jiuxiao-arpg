| **现状** | 实测数字 + 代码位置（函数名，不写行号 —— 行号会漂） |

## 2. 逐条方案

### P01 · 任务怪数量少，要开几次图才能刷满

**现状**

- 任务击杀需求最大 **80 只**（`QUESTS` 里 `killAny` 的 count 有 20/25/30/35/40/45/50/60/65/70/80 若干档）。
- 世界图一次刷 **40~46 只**（`MAPS[x].spawnCount`），副本图 12 只。
- 怪**死了不补刷**：`spawnEnemies` 只在 `loadMap` 时刷一次，`updateEnemies` 里没有补位逻辑。

所以「杀 80 只」的任务必然要出图再进图，最多三次。用户的原话是「要开地图几次才能刷满」。

**根因**：任务需求量是按「这张图的总怪数 × 倍率」估的，但估的时候没考虑「玩家不会把图清空」——
实际清场成本很高（跑图 + 找怪），而且清完就没了。

**改法**（建议 A，两条一起做）

- **A1 地图内补刷**（`src/game.js`）：`updateEnemies` 里加一个低频补位器 ——
  每 6 秒检查一次，若「本图存活怪数 < `spawnCount × 0.6`」且「当前 zone 离玩家 > 25 米」，
  就在该 zone 补 1~2 只（上限不超过 `spawnCount`）。
  只在**野图**生效（`MAPS[id].raid` / `safe` / 地下城 / 试炼全部跳过）。
  这和「同屏上限 PC 36 / 触屏 28」不冲突：补位只补到 `spawnCount`，超出的照旧被 cap 截断。
- **A2 任务量对齐**（`src/data/data-quests.js`）：把 `killAny` 的 count 统一压到
  **≤ 本图一轮能杀完的数量**（`spawnCount × 0.8`，即 32~36）。现存的 45/50/60/65/70/80
  逐条改小，并把「多杀」的爽感转成「多刷几只精英」——即这些任务改成 `killElite` 或 `killAny` 但 count 降档。
- 备选 B：只做 A2（不改刷怪）。优点是零风险，缺点是「图清空了要等重进」的体验还在。
  **建议 A1+A2 都做**，A1 是玩家真正想要的东西。

**验收**

- 接一条 80 只的主线（改完后应为 ≤36），在图里**不出图**杀满，`dev/quest-progress.js` 记录不重进图。
- 清空一张图后再等 30 秒，图上怪数回到 `spawnCount × 0.6` 以上。
- `node dev/zone-density.js` 仍然全绿（补位不改静态分配，只补运行时数量，密度校验读的是静态值 —— 要确认这一点没被破坏）。

**落地（2026-10-28）** ✅

- `game.js` 新增 `updateRespawn(dt)`（在 `updateEnemies` 之后每帧调用）：`RESPAWN_TICK 6` 秒一次、
  `RESPAWN_FLOOR 0.6`（低于计划总数 60% 才补）、`RESPAWN_MIN_DIST 25`（只在 25 米外的区补）、
  离玩家最远的区优先。安全区 / raid 图 / 地下城 / 试炼一律跳过。
- **一处偏离**：计划书写「一次补 1~2 只」，但同一节的验收线是「清空后 30 秒回到 spawnCount × 0.6」——
  41 只的图要在 5 个 tick 内补回 25 只，一次 1~2 只实测只补到 10 只（图看起来还是空的）。
  改成「按缺口的一半补、单次上限 `RESPAWN_BATCH = 5`」：5 tick × 5 = 25 刚好压线，
  而且怪都落在 25 米外，不会在玩家眼前凭空出现。
- `data-quests.js`：`killAny` 的 45/50/60/65/70/80 全部压到 **32~36**；
  **奖励同步按 `新数量 / 旧数量` 缩放**（xp 取整到百、gold 取整到五十）——
  只砍数量不砍奖励等于把悬赏变成最划算的刷钱途径，P16 刚把符文口子收掉，不能这边又开一个。
- 验证：`node dev/respawn-check.js`（14 项：清空后补位 / 上限 / 距离 / 只补野图 / 任务量对齐）。

### P02 · Boss 在传送门那边也放技能

**现状**（`src/game.js` `updateBossAI`）

```js
if (e.patternCd <= 0) {
  e.patternCd = RND(4.5, 7.5) * (1 - e.phase * 0.12);
  this.bossPattern(e, pp);      // ← 没有任何距离判定
}
```

**根因**：技能 CD 到点就放，不看玩家在多远。Boss 一旦被激活（`d < 17` 那一瞬间 `e.active = true`），
哪怕玩家跑回入口，它照样每 4.5~7.5 秒放一次 `ringshot`（12 发弹幕，`life: 3s × speed: 12` = 36 米射程）、
`slam`（在**玩家脚下**生成 4.6 米预警圈）。`slam` 尤其离谱 —— 它把落点直接钉在玩家坐标上，
所以玩家站在 98 米外的传送阵旁，脚下照样亮红圈。

**改法**

1. **技能距离闸**：`bossPattern` 入口加判定
   ```js
   const d = DIST2D(e.pos, pp);
   if (d > BOSS_SKILL_RANGE) { e.patternCd = 1.2; return; }   // 短 CD 重试，不消耗整轮
   ```
   `BOSS_SKILL_RANGE` 建议 **18 米**（略大于激活半径 17，让「刚激活就能放」）。
   写进 `BALANCE.boss.skillRange`，按难度可调。
2. **脱战**：`updateBossAI` 里加
   ```js
   if (d > BALANCE.boss.leash) { /* 玩家跑出 32 米 → 回位、清 debuff、回满血、active=false */ }
   ```
   回位时 `this.boss = null; UI.updateBoss(null)`。**这是标准 ARPG 的 leash 机制**，
   顺带解决 P10 的「卡位远程打死」——玩家跑远，Boss 回满血，卡位就没意义了。
3. **`slam` / `roots` 的落点不要钉在玩家身上**：改成「以 Boss 为圆心、朝向玩家的扇形/圆形」，
   或「玩家当前位置 + 0.5 秒预判」。现在的写法等于全图追踪，玩家跑多远都躲不掉（只是看不见）。

**验收**

- 站在入口传送阵不动，Boss 区 98 米外的 Boss 60 秒内**不放任何技能**（`dev/probe-boss.js` 打点统计）。
- 走进 18 米内，技能正常释放。
- 打一半跑出 32 米，Boss 回位 + 血条消失 + 回满血。

**落地（2026-10-28）** ✅

- `data-core.js`：`BALANCE.boss.skillRange = 18` / `leash = 32`。
- `game.js` `updateBossAI`：CD 到点先量距离，`> 18` 米只把 CD 压到 1.2 秒重试（不放技能）；
  `> 32` 米走新增的 `resetBoss(e)`。
- `resetBoss` 一次做满六件事：回锚点 / 回满血 / 清 debuff / 清技能态（windup·charging·pendingMelee）/
  `phase` 归零 / `dmg` 退回 `baseDmg`。少了「退伤害」这条，反复拉远拉近能把首领养成一拳超人。
- `_bossAim(e, pp, spread)`：`slam` / `roots` / `rocks` / `meteor` / `swordrain` 的落点全部改成
  「玩家位置 + 散布 → 夹进 18 米」，不再钉在玩家脚下。
- 验证：`node dev/probe-boss.js` 第一、二、四段（距离闸 25 米测、脱战 40 米测、落点 400 次采样）。
  **注意**：测距离闸不能取 60 米 —— 那个距离先触发的是脱战，验不到闸。

### P03 · 小地图方向 / 箭头不对；要能点击放大 + 滚轮缩放

**现状**（`src/ui-minimap.js`）

- 第 184/277 行有两处 `g.rotate(Math.atan2(Game.playerFace.x, Game.playerFace.z))`。
- 地图本身是「整图俯视」，`tx = R + (x - cx) * scale`、`tz = R + (z - cz) * scale`，**不做旋转**。
- 面板固定尺寸（`R` 由 canvas 尺寸算），没有缩放状态。

**根因**（待实测确认，两个可能）

1. **箭头方向错**：`atan2(x, z)` 得到的是「以 +z 为 0、顺时针」的角度，而 canvas 的 `rotate()`
   是「以 +x 为 0、顺时针」。两者差 90°，所以箭头会整体偏一个直角。修法是 `atan2(x, z)` → `atan2(x, z)` 后再 `- Math.PI/2`，
   或者画箭头时把三角形朝向画在 +x。
2. **地图与箭头不一致**：地图是「北在上」的固定朝向，如果箭头按玩家朝向转、地图不转，
   玩家会觉得「箭头指的方向和地图上的路对不上」。两种做法二选一：
   - **A 北固定**（推荐，暗黑 2 式）：地图不转，箭头按「玩家朝向相对北的角度」转。
   - **B 玩家朝上**：整张地图随玩家旋转（`g.rotate(-faceAngle)`），箭头永远朝上。
     B 更像手游，但小地图是「整图俯视」不是「局部视野」，转起来容易晕。

**改法**

1. **先修箭头**（`drawPlayerArrow`）：确认角度基准，加一条断言 —— 玩家朝 +z（`playerFace = {x:0,z:1}`）时，
   箭头必须指向屏幕下方（因为 +z 在 canvas 上是向下）。写进 `dev/minimap-check.js`。
2. **点击放大**：小地图加 `click` → 打开一个居中大面板（复用 `#minimapPanel` 的样式体系，
   新建 `#mapBig` 层），尺寸 `min(80vh, 80vw)`。
3. **滚轮缩放**：`#mapBig` 上绑 `wheel`，`scale` 范围 **0.5×~4×**，以鼠标位置为锚点缩放
   （不是以中心，否则放大后想看的地方跑掉）。同时支持双指捏合（`touchmove` 两指，复用 `mobile.js` 的判定）。
4. 放大后**显示坐标格 + 区域名**，并保留「玩家 / 任务区 / 首领 / 出口门」四个标记。

**验收**

- `dev/minimap-check.js`：玩家朝 +z / +x / -z / -x 四个方向，箭头像素方向分别朝下 / 右 / 上 / 左。
- 点小地图能开大图，滚轮缩放后鼠标指的那一点不动（误差 < 8px）。
- 移动端双指缩放可用，且不影响摇杆。

**落地（2026-10-28）** ✅

- `_faceAngle()` 改成 `atan2(f.z, f.x)`。旧代码 `atan2(x, z)` 分子分母反了：±x 方向恰好对，
  ±z 方向整整差 180°（朝南走、箭头指北），所以玩家「有时候看着对、转两圈就发现不对」。
- 箭头绘制 `+π/2`（三角形是朝上画的，而 `_faceAngle` 给的是「朝 +x」的角度）。
- `#mapBig` 大图：720×720 画布，复用同一套 `paint()`；缩放 0.5~4×，**以鼠标位置为锚点**；
  拖动平移（pointer 事件）、双指捏合、Esc / × / 点遮罩关闭；1.25× 以上画 25 米坐标格 + 区名。
- 顺手修了一个真 bug：`#miniWrap` 在 `#app` 下默认 `pointer-events:none`，点击根本到不了容器，
  代码里绑的 click 永远不触发。CSS 里显式打开（这是自测时才暴露的，纯看代码看不出来）。
- 验证：`node dev/minimap-check.js`（离线段四方向 + 缩放锚点 + 边界，浏览器段点开/滚轮/拖动/Esc/×）。

### P04 · 自动拾取 + 品质筛选

**现状**（`src/game.js` `updateLoot`）

- 掉落物有吸附圈（`pullR = 2.4 + pickupRadius × 0.55`）和拾取圈（`grabR = 1.3 + pickupRadius × 0.3`），
  但**装备必须走到 1.3 米内才捡**，且行囊满了会一直弹「行囊已满」。
- 没有设置项（`src/core/settings.js` 里没有拾取相关字段）。

**改法**

1. **设置项**（`src/core/settings.js`，`index.html` 设置页加一块「拾取」）：
   - `autoPickup`：开 / 关（默认**开**）
   - `pickupMinRarity`：`common` / `magic` / `rare` / `epic` / `legendary`（默认 `magic`）
     —— 低于此品质的装备**不自动捡**（仍留在地上，走近照旧能手动捡）
   - `pickupGold` / `pickupMat` / `pickupRune`：三类非装备掉落单独开关（默认全开）
2. **逻辑**：`updateLoot` 里装备分支加
   ```js
   if (SETTINGS.autoPickup && RARITY_ORDER[l.item.rarity] >= RARITY_ORDER[SETTINGS.pickupMinRarity]) { ... 自动捡 ... }
   ```
   自动捡时**不弹「行囊已满」**，改成「自动拾取暂停」的一条低频提示（10 秒去重），
   否则一波怪掉 8 件会刷 8 条红字。
3. **「留在地上」要看得见**：不自动捡的装备，名牌上标一个「未拾取」小角标，
   否则玩家会以为东西没掉。

**验收**

- 设置成 `rare`，杀一波掉 5 件（3 白 1 蓝 1 金）→ 只有金自动进包，白蓝留在地上。
- 关掉自动拾取 → 行为回到现在的「走近才捡」。
- 行囊满时自动拾取静默暂停，不刷屏。

### P05 · 每图怪种太多 → 图鉴集齐太快；怪物总数扩到 120

**现状**

- `MONSTERS` 共 **80** 条（humanoid 8 / undead 16 / beast 20 / spirit 20 / plant 3 / stone 13）。
- 每图 `spawns` 怪种数：老图 12~13（`forest` 12、`swamp` 13、`mine` 13、`abyss` 12、`heaven` 12），
  新图 8~9，副本 3~4。**平均 6.44**。
- 图鉴（`CODEX`）按「收进过图鉴的怪种」计数。

**根因**：一张图 12 种怪 → 清一轮就解锁 12 个图鉴条目，30 张图不到 10 小时就收满。
种类多本来是「生态感」，但**一次全给你**就变成了「图鉴没难度」。

**口径已定（用户 2026-10-28 拍板）：怪物（非 boss）**种类** 80 → 120。**

用户原话：「怪物（非boss）种类80-120」。所以是**图鉴条目数**扩到 120，不是每图刷 120 只。

> 为什么不能是「每图 120 只」：与 §5.1 的「380~450㎡/只」直接冲突（290 尺寸图 16000㎡ / 120 = 133㎡/只，
> 密 3 倍），而且同屏上限 PC 36 / 触屏 28 会截断 —— 等于只有 36 只在动，剩下的白算。

**改法**

### P06 · 蓝耗太低，法师太强

**现状**

- 技能消耗（`src/data/data-skills.js`）：战士 12~40（均 23.1）、法师 10~50（均 28.5）、道士 8~45（均 26.5）。

**根因**（两条独立问题，用户 2026-10-28 明确要求**两条都改**）

1. **蓝耗**：消耗是**固定值**，蓝量是**线性成长**。等级越高「蓝/消耗」比值越大，40 级以后基本等于无限蓝。
   法师 CD 最短（火球 1.4s），无限蓝 = 无限输出。
2. **施法距离**：法师 `castRange` 是 12~16 米，比战士（3.2~11）远一个量级，而 Boss 技能最远也就 12~14。
   站在自己射程边缘 = 打得到对方、对方打不到你。

**改法**

1. **施法距离砍（用户点名）** —— `src/data/data-skills.js` 法师 8 个主动技能：

   | 技能 | 现在 | 改后 |
   |---|---|---|
   | 火球术 `fireball` | 16 | **12** |
   | 冰锥 `iceshard` | 14 | **11** |
   | 炎爆术 `meteor` | 16 | **13** |
   | 雷弧链 `chain` | 12 | **10** |
   | 火墙 `firewall` | 12 | **10** |
   | 暴雪 `blizzard` | 12 | **10** |
   | 冰霜新星 `frostnova` | 9 | **8** |
   | 焚天 `pyroclasm` | 0（自身范围） | 0（不动） |

   原则：**法师最远 13 米 < Boss 技能最远 14 米**（见 P02），这样「站远打」不再是无风险策略。
   道士的远程（符咒类）同步收到 12 米以内，避免下一个「法师」。
2. **消耗加大（用户点名「一个蓝条都用不完」）** —— 两刀一起：
   - **基础消耗上调**：法师火球 10 → 16、冰锥 14 → 20、雷弧链 22 → 30、火墙 26 → 34、

     skillCost(sk) = sk.cost * (1 + 0.06 * (sk.lv - 1))   // 10 级技能 = 1.54×

3. **压回灵**：`mpReg` 收益减半（`int` 成长 0.06 → 0.03，装备词缀同比例）。

4. **不动伤害**。用户说的是「距离远、不费蓝」，不是「伤害高」。先动距离和消耗，观察一周再决定要不要动倍率。

### P09 · 多 Boss 时血条显示的是另一只

**现状**（`src/game.js` `updateEnemies` + `updateBossAI`）

```js
if (e.boss && !e.active) {
  if (d < 17) { e.active = true; this.boss = e; UI.updateBoss(e); ... }   // 谁先靠近谁抢到血条
}
...
if (this.boss === e) UI.updateBoss(e);    // 只有 this.boss 那只更新血条
```

**根因**：`this.boss` 是**单个引用**，先激活的 Boss 占住它。玩家走进第二只 Boss 的 17 米，
`this.boss` 被抢走 → 血条换成第二只；玩家回头打第一只，第一只在掉血，
但 `this.boss !== 第一只`，所以血条**不更新**。正是用户描述的「实际打的在掉血，血条不动」。

5 张老图有多只 Boss：`forest`(2) / `swamp`(3) / `mine`(2) / `abyss`(3) / `frost`(2)。

**改法**

`this.boss` 的语义从「谁先靠近」改成「**玩家最近攻击的那只**」：

1. `damageEnemy` 里，若目标是 boss → `this.boss = e`（打谁显示谁）。
2. `updateBossAI` 里 `if (this.boss === e)` 保留（只更新当前血条）。
3. 没有攻击行为时，`this.boss` 取「**离玩家最近的 active boss**」（每 0.5 秒重算一次，
   避免每帧遍历），并在切换时给血条一个淡入，让玩家知道换了。
4. 多 Boss 同时在场时，血条下方加一排小血条（每条 60px，显示另外几只），
   点小血条可切换主显示 —— 这是 ARPG 的标准做法（暗黑 3 的精英群血条）。

**验收**

- `swamp`（3 只 Boss）：打 A 时血条是 A 且在掉；走到 B 旁边不动手，血条仍是 A；
  打 B，血条切成 B；再回头打 A，血条切回 A 且数字连续。
- `dev/probe-boss.js` 加一条：任意时刻 `UI` 显示的血条 hp === `this.boss.hp`。

**落地（2026-10-28）** ✅

- `damageEnemy`：每次命中把 `this.boss` 钉在目标身上 —— **攻击是唯一的主动切换途径**。
- `_pickBoss`：改成**粘性**而不是「每 0.5 秒按距离重选」。当前那只还活着就不换；它死了 /
  脱战了才去找「最近的已激活首领」；一只都没有就收血条。
  原方案（1.5 秒锁 + 就近）在多首领只相距 9~10 米的图上会让血条随走位来回跳，
  和「打谁看谁」的验收要求正好相反。
- `ui.js`：多首领时主血条下面加一排 60px 小血条，点一下切主显示；切目标时血条闪一下；
  按「存活首领 + 血量百分比 + 当前目标」做指纹，指纹没变不重建 DOM（`updateBoss` 是每帧调的）。
- 验证：`node dev/probe-boss.js` 第三段（打 A / 站 B 旁边 / 打 B / 回打 A / A 死接 B / 全灭收血条）。

### P10 · 卡位远程打死 Boss；法师技能几乎全图

**现状**

- 所有技能**都有** `castRange`（`data-skills.js` 全部主动技能已核，无遗漏）。
- 但 `resolveCast(sk, pp, aim, dir)`（`game.js`）只做**夹落点**，不做拒绝：
  ```js
  if (range > 0 && dist > range) out.copy(pp).addScaledVector(to.normalize(), range);
  ```
  玩家在 30 米外点火球 → 落点被夹到 16 米，**技能照放**（扣蓝、进 CD），只是打空。
- `cast === 'enemy'` 分支还会 `nearestEnemy(pp, maxR)` **自动改锁最近的敌人** ——
  所以「朝远处点」的实际效果是「打身边 16 米内最近的怪」，玩家根本感觉不到距离限制。
- `const maxR = range || 99`：`castRange` 为 0 / undefined 时上限变 99 米。
  当前没有技能触发（全都显式写了），但这是**将来新增技能必踩的坑**。
- Boss 被激活后没有 leash（见 P02），所以能站高台 / 石头后面一直打。

**根因**：射程只用来「裁剪落点」，没用来「否决施法」。真正限制输出的不是射程，
是「有没有目标」—— 而 `nearestEnemy` 会帮你找。**射程对玩家不构成任何约束。**

**改法**

1. **硬拒绝**（`game.js` 的 `castSkill`，放在扣蓝之前）：
   ```js
   if (sk.castRange > 0 && sk.cast !== 'self') {
     const d = (sk.cast === 'dir') ? distToNearestEnemy(pp) : DIST2D(pp, aim);
     if (d > sk.castRange * 1.05) { UI.log('距离太远。', 'bad'); return; }  // 不扣蓝、不进 CD
   }
   ```
   注意 `cast === 'dir'`（火球 / 突刺）是「朝朝向飞」，玩家点的位置无所谓，
   要校验的是「最近敌人是否在射程内」，不是「点击位置」。
2. **去掉 `|| 99` 兜底**：`const maxR = range > 0 ? range : 0;` —— 没射程就是不能自动锁敌。
3. **Boss leash**（与 P02 合并做）：玩家跑出 32 米 / Boss 8 秒摸不到人 → 回位 + 回满血。
   卡位流的核心不是「打得远」，是「Boss 不会回来」。
4. **数据校验**：新增 `dev/skill-ref.js`，断言每个非 `self` 技能 `castRange > 0`
   且 ≤ 14（与 P02 的 Boss 技能上限对齐）。

**验收**

- 站在 30 米外对 Boss 点火球 → 提示「距离太远」，不扣蓝、不进 CD。
- 卡在石头上打 Boss，Boss 走不过来 → 8 秒后回位并回满血（日志「XX 已退回祭坛」）。
- 法师技能面板能看到射程（`ui-skills.js:654` 已支持），且最大值 ≤ 13（P06 定的数）。

**落地（2026-10-28）** ✅

- `game.js` 新增 `castRangeFail(sk)`，在**扣蓝之前**拦一道：够不着就 `UI.log('距离太远。')`
  直接 return —— 不扣蓝、不进 CD、不触发任何后续结算。
- 三种 `cast` 分开判，不能图省事写成一个：
  · `self` 不判（自身范围技能没有「太远」这回事）；
  · `dir` 判**最近敌人**，不是点击位置 —— 朝朝向飞出去的技能点哪儿都无所谓，
    附近一个怪都没有时**放行**（空放是玩家自己的事，连按都按不出来会让人以为技能坏了）；
  · `ground` / `enemy` 判落点距离。容差 5%（落点由屏幕射线反算，差一点点正常）。
- `resolveCast` 去掉 `const maxR = range || 99` → `range > 0 ? range : 0`：
  没写 `castRange` 就是不能自动锁敌，不再是「白送 99 米」。
- Boss leash 与 P02 合并做（`BALANCE.boss.leash = 32`），已随第 1 批落地。
- 验收：`node dev/skill-ref.js` 第三节（30 米外拒绝 / 不扣蓝 / 不进 CD / 射程内正常扣蓝进 CD）。
  **注意**：测「30 米外打首领」必须先把杂兵标死 —— `dir` 类技能判的是最近敌人，
  身边有杂兵时闸门本来就不该触发（火球确实打得到杂兵，那不是 bug）。

### P12 · 试炼升级太快 —— 难度随等级涨 + 传世挂高波

**现状**（`src/data/data-trial.js`，已核代码）

- `trialEnemyLevel(wave, playerLevel)` = `playerLevel + 1 + (wave-1) × 0.12` —— 怪物**等级**确实贴玩家。
- 但**难度乘区** `trialHpMul(wave)` / `trialDmgMul(wave)` **只跟波数有关，跟玩家等级无关**。
  前面挂的 `0.54 / 0.56` 是「主线怪物曲线重做」的补偿系数，按低等级调的。
- 经验 = `s.xpNext × ratio`（34% / 72% / 105%），**按「当前升级所需的比例」给**，不随等级衰减。
- 波次无限、`countMax: 22`、刷新快 → 单位时间经验远高于野图。

**根因（刷级的真正来源）**

不是「怪太弱」，是**经验按比例给 + 难度不随等级涨**这两条乘在一起：

- 40 级玩家刷第 1~10 波，血量乘区还是 `0.54 × (1 + 0.1w + 0.0045w²)`，而玩家装备/技能已经成型 → 一路平推；
- 每波照给 `0.34 × 升级所需` 的经验，**收益完全不随等级衰减**；
- 于是「低波数 × 高等级」= 零风险高收益。玩家不需要打高波，只需要反复重开。

**用户方案（2026-10-28 拍板）**

> 「动态根据人物等级来调整试炼场里的怪物难度，这样升级可以升难度也是增加的，这也是一种平衡。
> 并且试炼只有高级层数才有极小概率掉落传世装备。」

翻译成两条规则：

1. **难度锚点 = 波数 × 玩家等级** —— 等级涨了，同一波的怪也要变强，不能靠等级碾压前期波次。
2. **传世（unique）只在高级波数极小概率掉** —— 试炼的终局产出挂在高波，不挂在「重开」。

**改法**

1. **等级难度乘区**（`data-trial.js` 新增 `trialLevelMul(level)`）：

   ```js
   function trialLevelMul(level) {
     const L = Math.max(1, level || 1);
     return 1 + Math.max(0, L - 10) * 0.035;   // 10 级 ×1.00 · 30 级 ×1.70 · 60 级 ×2.75
   }
   ```

   `trialHpMul` / `trialDmgMul` 各乘上它。

   > **为什么从 10 级起算**：`unlockLevel: 6`，6~10 级是「刚解锁、装备没成型」的窗口，
   > 这段不该加压；10 级后进卷二，装备开始滚雪球。
   > **系数 0.035 是初值**，用 `dev/trial-balance.js` 跑「各等级首次崩盘波数」校准，
   > 目标 **10/20/30/40/50/60 级的最远波数都落在 25~40 波**（现在高等级能推到 60+）。

2. **经验按「波数 ÷ 等级」衰减**（止住刷级的关键，比调难度更直接）：

   ```js
   const pace = Math.min(1, wave / Math.max(1, s.level * 0.6));   // 40 级要打到第 24 波才满额
   ratio *= pace;
   ```

   | 玩家等级 | 第 1 波给多少 | 打满额需要 |
   |---|---|---|
   | 15 | 11% × 0.34 | 第 9 波 |
   | 40 | 1.4% × 0.34 | 第 24 波 |
   | 60 | 0.9% × 0.34 | 第 36 波 |

   **效果**：想靠试炼升级必须往高波打，而高波本来就难 —— 这正是用户说的「升级难度也增加」。

3. **传世掉落：只在高级波数**（`data-trial.js` 加 `TRIAL_UNIQUE` + `trial.js` 的 `onWaveCleared`）：

   ```js
   const TRIAL_UNIQUE = { minWave: 30, base: 0.003, perWave: 0.0004, cap: 0.019, bossMul: 3 };
   ```

   | 波数 | 普通波 | 首领波（×3） |
   |---|---|---|
   | 30 | 0.30% | 0.90% |
   | 40 | 0.70% | 2.1% |
   | 50 | 1.1% | 3.3% |
   | 60 | 1.5% | 4.5% |
   | 70+ | 1.9%（封顶） | 5.7% |

   - **只掉 `ilvl ≥ 40` 的传世**（`data-uniques.js` 的 40 件本来就全部 ilvl ≥ 40）。
   - **玩家 < 39 级不掉**（`reqLv = ilvl - 1`，39 级才穿得上 40 级装）——
     避免「20 级捡到传世但穿不上」的挫败感。
   - 走 `rollUnique(ilvl)`（`src/items.js` 已有），「未收集优先」沿用主线规则。
   - 每波最多 1 件，抽样 10 万次验概率。

4. **不设「20 级上限」**（用户没选这个方案）：门槛保留 `unlockLevel: 6`，
   用「难度随等级涨 + 经验随波数衰减」代替一刀切。老档和高等级玩家都能继续玩试炼，只是拿不到白给的经验。

**验收**

- `dev/trial-balance.js` 新增两段：① 各等级最远波数落在 25~40；② 传世概率抽样与上表一致（±10%）。
- 40 级角色打 10 波：经验总量 **< 升级所需的 15%**（现在约 340%）。
- 40 级角色打 30 波：能掉传世，1000 次抽样出 2~5 件。
- 25 级角色打 60 波：**不掉传世**（等级不够，`reqLv` 卡住）。

**落地（2026-10-28）** ✅

- `data-trial.js`：`trialLevelMul(level)` = `1 + max(0, L − 10) × 0.035`，乘进 `trialHpMul` / `trialDmgMul`
  两个乘区（10 级 ×1.00 · 30 级 ×1.70 · 60 级 ×2.75）；不传 `level` 时按 ×1.00，老调用点不会静默变难。
- `trialXpPace(wave, level)` = `(wave / (level × 0.6)) ^ 3`，`onWaveCleared` 里 `ratio *= pace`。
- `TRIAL_CFG.unique` + `trialUniqueChance`：30 波起 0.3%，每波 +0.04%，封顶 1.9%，首领波 ×3；
  只掉 `ilvl ≥ 40` 的传世，玩家 < 39 级不掉（`reqLv` 卡死，掉了也穿不上）。每波最多 1 件。
- **两处偏离计划书**（都是实测后改的，写在这里免得下次又「按文档改回去」）：
  1. 经验衰减从**线性**改成**三次方**。线性实测：40 级打 10 波仍给 115% 升级所需，离验收线
     （< 15%）差一个量级 —— 因为 10 波只要几分钟。三次方后 ≈ 13%，满额波数不变（仍是第 24 波）。
  2. 「各等级最远波数落在 25~40」在这套模型下**拿不到**：`dev/trial-balance.js` 的崩盘线是
     「贴身 25% 同屏、可撑 6 秒」，P12 之前的基线本身就是 16~20 波（不是 25~40）。
     改成**相对口径**验收：60 级比 10 级早崩 3 波；同一波的 TTK 随等级上升（60 级是 10 级的 1.4 倍）。
     绝对值要抬到 25~40 是另一件事（松 0.54 补偿系数），不在 P12 范围。
- 验证：`node dev/trial-check.js`（53 项）+ `node dev/trial-balance.js` 新增「各等级最远波数 / 同波强度」两段。

   - 例：`2-2` 的 canyon 用「窄峡谷（走廊宽 0.10R）」，`3-2` 用「宽谷 + 侧洞（0.18R + 2 个耳室）」
   实现上给 `ZONE_ARCHETYPES[x]` 加第二个参数 `variant`，同一种骨架出 2~3 套坐标表。
3. **每章一个「主题规则」**：卷一的图必须有一条「贯穿南北的主路」，卷三的图必须「绕一圈回到入口」…
   这条是设计约束，写进 `AGENTS.md` 供以后加图时遵守。
